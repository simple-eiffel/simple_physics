Architecture Overview

simple_physics is organized into three conceptual layers:

  • Foundation Layer: Core mathematical types (VECTOR_3D, BODY_TYPE)
  • Domain Layer: Physics concepts (PHYSICS_BODY, PHYSICS_WORLD)
  • Integration Layer: Numerical methods (PHYSICS_INTEGRATOR, collision detection)

Design Principles

1. Single Responsibility

Each class has one reason to change:

  • VECTOR_3D — Only responsible for vector math
  • PHYSICS_BODY — Only responsible for body state (mass, position, velocity)
  • PHYSICS_WORLD — Only responsible for coordinating bodies and gravity
  • PHYSICS_INTEGRATOR — Only responsible for numerical integration (RK4)
  • COLLISION_DETECTOR — Only responsible for detecting collisions
  • COLLISION_RESOLVER — Only responsible for computing collision responses

2. Immutability of Results

Operations return new objects rather than modifying state:

-- ✓ Immutable: Returns new vector
l_result := v1.add (v2)

-- ✗ Wrong: Can't modify in place
v1.x := 10.0  -- Error: read-only

Exception: Commands like set_position modify the body itself (since bodies are stateful).

3. Separation of Concerns

Public API is separate from implementation:

Concern Responsibility Location
Vector Math Component access, arithmetic VECTOR_3D
Physics State Mass, position, velocity PHYSICS_BODY
World State Bodies, gravity, collision list PHYSICS_WORLD
Integration RK4 numerical method PHYSICS_INTEGRATOR
Collision Detection Sphere-sphere collision COLLISION_DETECTOR
Collision Response Impulse calculations COLLISION_RESOLVER

4. Design by Contract

Every public feature has explicit contracts:

  • Preconditions: What must be true before calling (caller's responsibility)
  • Postconditions: What will be true after (provider's responsibility)
  • Invariants: What must always be true (class's responsibility)

Example:

add (other: VECTOR_3D): VECTOR_3D
    require
        other_not_void: other /= Void
    ensure
        result_not_void: Result /= Void

No Inheritance Chains

By design, simple_physics avoids deep inheritance hierarchies. Each class inherits directly from ANY:

  • Benefit: Simple, flat hierarchy — easy to understand
  • Benefit: Composition over inheritance
  • Trade-off: Some code duplication in data classes

Collision Processing Pipeline

Phase 1: Detection

COLLISION_DETECTOR identifies colliding pairs:

  1. For each body pair (A, B):
  2. Calculate distance between centers
  3. If distance < radius_a + radius_b, collision detected
  4. Create COLLISION_INFO with contact geometry

Phase 2: Resolution

COLLISION_RESOLVER computes impulse response:

  1. For each COLLISION_INFO:
  2. Calculate relative velocity at contact point
  3. Apply impulse along collision normal
  4. Update body velocities
  5. Create COLLISION_RESULT with post-collision velocities

Phase 3: Integration

PHYSICS_WORLD orchestrates both phases:

integrate_step (dt)
    │
    ├── Run PHYSICS_INTEGRATOR.step(dt)
    │   └── Update positions and velocities (RK4)
    │
    ├── Run COLLISION_DETECTOR.detect()
    │   └── Find all collisions
    │
    ├── For each collision:
    │   Run COLLISION_RESOLVER.resolve()
    │   └── Apply impulses
    │
    └── Return PHYSICS_RESULT
        └── Collision count and success flag

RK4 Integration

Why RK4?

Fourth-order Runge-Kutta provides:

  • Accuracy: O(h⁵) error per step (h = time step)
  • Stability: Good for typical physics parameters
  • Efficiency: 4 force evaluations per step (better than naive methods)

Algorithm


Given: position p, velocity v, forces F, time step dt

k1 = F(p, v)
k2 = F(p + 0.5*dt*v, v + 0.5*dt*k1)
k3 = F(p + 0.5*dt*(v + 0.5*dt*k2), v + 0.5*dt*k2)
k4 = F(p + dt*(v + 0.5*dt*k3), v + 0.5*dt*k3)

p_new = p + dt * (v + dt/6 * (k1 + 2*k2 + 2*k3 + k4))
v_new = v + dt/6 * (k1 + 2*k2 + 2*k3 + k4)

Time Step Recommendations

Time Step FPS Accuracy Use Case
0.008 (125 Hz) — Very High High-speed collisions, precision
0.016 (60 Hz) 60 FPS High Real-time visualization (default)
0.033 (30 Hz) 30 FPS Medium Slower systems only

Extension Pattern

Adding new features follows this pattern:

  1. Create new immutable data class (e.g., TORQUE)
  2. Add feature to PHYSICS_BODY with contracts
  3. Update PHYSICS_INTEGRATOR computation
  4. Add tests to verify new behavior
  5. Update documentation

Performance Characteristics

Time Complexity

Operation Complexity Notes
Vector arithmetic O(1) Constant time
Body creation O(1) Constant time
Add/remove body O(1) List append/removal
Collision detection O(n²) All pairs checked
Integration step O(n) Update all bodies (4 force evals)
Full step O(n²) Dominated by collision detection

Scaling Guidance

  • 1-50 bodies: Real-time on any modern machine
  • 50-200 bodies: Monitor performance, may need optimization
  • 200+ bodies: Requires spatial partitioning (Phase 2 feature)

Contract Verification

All tests verify contracts:

  • Preconditions: Validate error handling when violated
  • Postconditions: Verify expected results
  • Invariants: Check consistency after operations
